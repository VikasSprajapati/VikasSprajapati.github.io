Scenario questions, with step-by-step resolution

Use this pattern for every scenario: understand, reproduce, isolate, fix, verify, prevent.

1. An API that used to be fast is now slow in production. What do you do?
  1. Confirm and scope it: which endpoint, since when, how slow, for whom. Check if a release or traffic spike matches the start time.
  2. Look at monitoring and logs: response times, error rates, CPU, memory, database load.
  3. Isolate the layer: time the request in parts: network, application code, database, external API calls.
  4. If it's the database: find the slow query (slow query log or EXPLAIN), look for a missing index, a full table scan or an N+1 pattern.
  5. Fix: add an index, rewrite the query, batch or eager-load, add caching (Redis or in-memory) for data that rarely changes, paginate large results.
  6. Verify: compare response times before and after under similar load.
  7. Prevent: add monitoring and an alert on response time, and a performance check in the release process.
2. A React page loads slowly. How do you fix it?
  1. Measure first: Lighthouse and the browser Performance tab. Check LCP, INP and CLS.
  2. Check the bundle: find large packages, and split code with lazy loading (React.lazy, dynamic imports) per route. I cut one app's main bundle from 814 kB to 123 kB this way.
  3. Check network: compress images, use modern formats and lazy-load them, cache API responses (for example with TanStack Query).
  4. Check rendering: find unnecessary re-renders with React DevTools Profiler, then use memo, useMemo or useCallback where it actually helps, and virtualise long lists.
  5. Verify and monitor: re-run Lighthouse and compare.
3. Duplicate orders or records are being created. How do you debug and fix it?
  1. Find the pattern: are the duplicates from the same request time, user double-clicks, retries or webhooks delivered twice?
  2. Check logs for the same request or event ID appearing twice.
  3. Fix at three levels: disable the button after the first click, make the API idempotent (idempotency key or unique order ID), and add a database unique constraint as the final safety net.
  4. Clean up: find duplicates with GROUP BY ... HAVING COUNT(*) > 1 and merge or remove them safely.
  5. Verify with a test that sends the same request twice.
4. Users are randomly logged out. What do you check?
  1. Token or session expiry time: is the access token too short, and is the refresh flow working?
  2. Whether the refresh token call fails or races (two requests refreshing at once).
  3. Cookie settings: domain, SameSite, Secure, and whether a proxy or load balancer drops them.
  4. Session storage: if sessions are in server memory and there are multiple servers, a shared store like Redis or the database is needed.
  5. Clock differences between servers that break token validation.
  6. Fix the cause, then test with an expired token and with two tabs.
5. A release broke production. What do you do?
  1. Stabilise first: roll back to the last good version if impact is high, and tell stakeholders.
  2. Find the cause from logs, error monitoring and the release diff.
  3. Fix on a branch, add a test that reproduces the bug, and review it.
  4. Release through UAT and check the fix in production.
  5. Write a short post-mortem: cause, fix and what we add to prevent it, such as a regression test or checklist item.
6. A third-party API is down or very slow. How does your app cope?
  1. Set timeouts so requests don't hang.
  2. Retry only safe requests, with exponential backoff, and stop after a limit.
  3. Use a circuit breaker or a failure counter so the app stops calling a broken service.
  4. Show a clear fallback to the user, such as cached data or a "try again" message.
  5. Queue work that can wait and process it when the service recovers.
  6. Log and alert, and keep the response and request IDs for support.
7. A SQL query takes 20 seconds. How do you optimise it?
  1. Run EXPLAIN to see whether it uses an index or scans the whole table.
  2. Add an index on the columns used in WHERE, JOIN and ORDER BY (a composite index when they are used together).
  3. Select only the columns needed, not SELECT *.
  4. Avoid functions on indexed columns in WHERE, and avoid N+1 queries.
  5. Paginate, and consider caching or a summary table for heavy reports.
  6. Compare timing before and after.
8. The frontend and backend teams disagree on an API contract. What do you do?
  1. Write down the exact request and response: fields, types, errors and status codes.
  2. Agree it in a short document or an OpenAPI spec that both teams review.
  3. Mock the API so the frontend can continue while the backend finishes.
  4. Validate on both sides (for example with Zod), and use versioning when a change would break clients.
9. A stakeholder keeps changing requirements mid-sprint. How do you manage it?
  1. Confirm the goal behind the change, not just the request.
  2. Explain the impact on time and other work, in plain words.
  3. Offer options: add it to the next sprint, swap it for a lower-priority item, or reduce the scope.
  4. Get the decision in writing and update the ticket and the acceptance criteria.
10. Your app has a security issue (SQL injection or XSS). How do you prevent and fix it?
  • SQL injection: use parameterised queries or an ORM, never string concatenation. Validate input.
  • XSS: escape output (React escapes by default; avoid dangerouslySetInnerHTML), and set a Content Security Policy.
  • CSRF: CSRF tokens (Laravel includes them) or SameSite cookies.
  • Secrets: keep them in environment variables or a secrets manager, never in Git.
  • Auth: hash passwords, limit login attempts, and use short-lived tokens with HTTPS.
  • If found: patch, check logs for abuse, rotate any exposed secrets and add a test.
11. How would you add caching with Redis to a slow endpoint?
  1. Identify data that is read often and changes rarely.
  2. On a request: check Redis by a key first; on a miss, query the database and store the result with a time-to-live (TTL).
  3. Invalidate or update the key when the data changes.
  4. Watch for stampedes (many requests missing at once) and stale data.
  5. Measure the hit rate and the response time.

Also useful for sessions and rate limiting.

12. A bug exists only on one developer's machine, or only in production. What do you do?
  1. Compare environments: versions, environment variables, config, data and operating system.
  2. Check logs and the exact input that triggers it.
  3. Reproduce with the same data in a staging environment.
  4. Fix and add a test. Use the same configuration in all environments, ideally with containers or a documented setup.

Frontend questions

What is the virtual DOM?

A lightweight copy of the UI in memory. When state changes, React builds a new virtual tree, compares it with the old one (diffing) and updates only the parts of the real DOM that changed. This makes updates efficient.

useState vs useEffect vs useRef vs useMemo vs useCallback?
  • useState: state that triggers a re-render when it changes.
  • useEffect: side effects after render (fetching, subscriptions). The dependency array controls when it runs, and the returned function cleans up.
  • useRef: a value that persists without causing a re-render, or a reference to a DOM element.
  • useMemo: caches a calculated value. useCallback: caches a function. Use them only when there is a measured performance need.
Why do lists need a key?

The key lets React identify which items changed, were added or removed. Use a stable unique ID, not the array index when the list can reorder.

Controlled vs uncontrolled components?

Controlled: React state holds the input value and updates it through onChange. Uncontrolled: the DOM holds the value and you read it with a ref when needed. Controlled is the default for forms with validation.

How do you manage state in a bigger React app?

Keep state local where possible, lift it up when siblings share it, use Context for rarely changing global values (such as theme or user), and use a library for complex or shared state. For server data I use TanStack Query, which handles caching, refetching and loading states.

Next.js: SSR vs SSG vs CSR?
  • CSR: rendered in the browser. Good for dashboards behind login.
  • SSR: rendered on the server per request. Good for fresh, SEO-sensitive pages.
  • SSG: rendered at build time. Fastest, for content that rarely changes.
Closures, the event loop, promises and async/await?
  • Closure: a function that remembers variables from the scope where it was created.
  • Event loop: JavaScript is single-threaded. Synchronous code runs first, then microtasks (promise callbacks), then macrotasks (timers).
  • Promise: represents a future value (pending, fulfilled, rejected). async/await is cleaner syntax on top, with try/catch for errors. Use Promise.all to run independent calls in parallel.
== vs ===, let vs const vs var?

=== compares value and type without conversion, so prefer it. const and let are block-scoped; const can't be reassigned. var is function-scoped and hoisted, so avoid it.

TypeScript: interface vs type, any vs unknown, generics?
  • interface vs type: both describe shapes. Interfaces can be extended and merged. Types can also describe unions and other forms.
  • any vs unknown: any turns off type checking. unknown must be checked or narrowed before use, so it's safer.
  • Generics: reusable types with a parameter, such as function first<T>(a: T[]): T.
  • Useful utility types: Partial, Pick, Omit, Record.
Flexbox vs Grid, and how do you make a page responsive?

Flexbox lays out in one dimension (a row or column). Grid lays out in two dimensions. For responsive design I use a mobile-first approach with relative units, Tailwind breakpoints (sm:, md:, lg:), and test at phone, tablet and desktop widths.

How do you improve accessibility?

Semantic HTML, labels on inputs, alt text, keyboard navigation with visible focus, enough colour contrast, and ARIA only when semantic HTML isn't enough.

Backend questions

Explain Laravel's MVC and request lifecycle.

A request goes through public/index.php to the HTTP kernel, then global middleware, then the router, which finds the route. Route middleware runs (such as auth), then the controller. The controller uses models (Eloquent) to read or write the database and returns a response, such as JSON or a view (Blade).

Eloquent ORM, migrations and the N+1 problem?
  • Eloquent: maps tables to model classes with relationships (hasMany, belongsTo).
  • Migrations: versioned scripts that change the database structure, so every environment stays in sync.
  • N+1: looping over records and running one query for each related record. Fix it with eager loading: Order::with('items')->get().
Middleware, validation, queues and the service container in Laravel?
  • Middleware: code that runs before or after a request, for example authentication or rate limiting.
  • Validation: $request->validate([...]) or a Form Request class.
  • Queues: run slow work (emails, imports) in the background through a worker.
  • Service container: resolves class dependencies automatically (dependency injection).
Node and Express: how do you structure an API?

Routes, controllers for the request handling, a service layer for business logic, a data layer (ORM) for the database, middleware for auth, validation and error handling, and central error responses with consistent status codes. I validate input with Zod and keep configuration in environment variables.

FastAPI vs Django vs Flask?
  • Flask: small and flexible, you add what you need.
  • Django: full framework with ORM, admin and authentication built in.
  • FastAPI: modern and fast, async, type hints and automatic validation and API docs.
Your main Python use is scripting. Say so, and say you'd use Laravel for the PHP side. Don't overclaim framework experience.
REST: methods, status codes and good API design?
  • Methods: GET reads, POST creates, PUT replaces, PATCH changes part, DELETE removes. GET, PUT and DELETE are idempotent.
  • Codes: 200 OK, 201 Created, 204 No Content, 400 bad request, 401 not authenticated, 403 forbidden, 404 not found, 409 conflict, 422 validation, 429 too many requests, 500 server error.
  • Design: nouns in URLs (/orders/123), consistent responses, pagination, filtering, versioning (/v1), clear error messages.
Authentication: session vs JWT vs OAuth 2.0?
  • Session: server stores the session, the client holds a cookie. Simple, easy to revoke.
  • JWT: a signed token with claims, stateless. Keep it short-lived and use a refresh token. It is harder to revoke before expiry.
  • OAuth 2.0: lets an app access another service on a user's behalf without their password. The user approves, the app gets an authorization code, exchanges it for an access token (and refresh token), and calls the API with it. I used this for Google Drive in Zob Connect.
Authentication vs authorization? How do you do role-based access?

Authentication proves who you are. Authorization decides what you can do. For role-based access I store a role per user and check it in middleware or policies on each protected route. In Zob Connect I used roles for HR, zone managers, site managers and team leads.

How do you handle webhooks safely?

Verify the signature, respond quickly with 200 and process in the background, make handlers idempotent by storing event IDs, and log failures so events can be replayed.

How do you handle errors and logging?

A central error handler, consistent error responses, no secrets or stack traces to the client, structured logs with a request ID, and alerts on error spikes.

Database questions

What is an index? When does it help or hurt?

A data structure (usually a B-tree) that lets the database find rows without scanning the whole table. It speeds up reads on columns used in WHERE, JOIN and ORDER BY, but slows down writes and uses space, so index what you query, not everything.

Joins, and the difference between INNER, LEFT and RIGHT?

INNER JOIN returns rows that match in both tables. LEFT JOIN returns all rows from the left table and matches from the right (nulls where none). RIGHT JOIN is the reverse.

Normalisation, and when to denormalise?

Normalisation splits data into related tables to avoid duplication and update problems (1NF, 2NF, 3NF). Denormalise on purpose when read speed matters more, for example a summary table for reports.

ACID and transactions?

Atomicity (all or nothing), Consistency (rules stay valid), Isolation (concurrent transactions don't interfere), Durability (committed data survives a crash). Use a transaction when several writes must succeed together, for example creating an order and reducing stock.

SQL vs NoSQL? When do you pick which?

SQL fits structured, related data and strong consistency (orders, payments, users). NoSQL (for example MongoDB or DynamoDB) fits flexible or very high-volume data, such as documents, logs or events. I've used SQL databases in production, and I know the NoSQL concepts.

What is Redis and what do you use it for?

An in-memory key-value store. Common uses: caching, session storage, rate limiting, queues and counters. Data has an optional time-to-live, and it's very fast because it is in memory.

How do you handle database changes safely?

Use migrations in version control, test them on a copy of production data, make changes backward-compatible where possible (add a column before removing one), take a backup, and have a rollback plan.

MySQL vs PostgreSQL?

Both are relational and reliable. PostgreSQL has richer features (advanced types like JSONB, stronger standards support). MySQL is simple and widely used. I've used both: MySQL in two platforms, and PostgreSQL in Zob Connect.

General engineering questions

Explain the SOLID principles.
  • S: Single Responsibility. A class or module has one reason to change.
  • O: Open/Closed. Open for extension, closed for modification. Add behaviour without editing tested code.
  • L: Liskov Substitution. A subclass should work wherever its parent is expected.
  • I: Interface Segregation. Prefer small, specific interfaces to one large one.
  • D: Dependency Inversion. Depend on abstractions, not concrete classes (dependency injection).

Example: a payment service that depends on a PaymentGateway interface, so adding a new gateway doesn't change the checkout code.

Git: merge vs rebase, and your branching workflow?

Merge keeps full history with a merge commit. Rebase replays your commits on top of the latest branch for a linear history (never rebase shared branches). My workflow: a task branch per ticket, a pull request with review, UAT, then production. I resolve conflicts locally and re-test before merging.

How do you keep code quality high?

Code review, small pull requests, linting and formatting, unit and integration tests, clear naming, no duplicated logic, and documentation of decisions. I also review AI-generated code the same way as any other code.

What do you test, and how?

Unit tests for logic (I wrote 65 on one project), integration tests for APIs and the database, and end-to-end tests for key user flows (Playwright). I test edge cases and failures, not just the happy path.

What is CI/CD?

Continuous Integration runs the build and tests on every push. Continuous Delivery deploys to an environment automatically or with one click. I use GitLab CI, and deploy with task branches, then UAT, then production.

Docker and microservices: what do you know?

Docker packages an app with its dependencies into a container that runs the same everywhere (a Dockerfile builds an image, and Compose runs several containers). Microservices split an app into small services that each own one capability and talk through APIs or events. They scale and deploy independently, but add complexity (networking, monitoring, data consistency), so I'd start with a well-structured monolith unless there's a clear need.

Be honest that you haven't used Docker or microservices in production, if that's the case.
How do you work with a remote, international team?

Clear written communication, short status updates, documented decisions, agreed overlap hours, and asking early when something is unclear. I've delivered a project with a four-person team and worked directly with stakeholders.

How do you use AI tools in development?

I use Claude Code, Cursor and Copilot for implementation, reviews, tests and debugging. I set the architecture and write the prompts, review every change, run the tests, and I'm responsible for what ships. AI makes me faster, but it doesn't replace understanding the code.

Tell me about a time you disagreed with a teammate or stakeholder.

Use a real example. Shape: the disagreement, how you listened to their reason, what data or example you used, and the outcome. End with what you learned.

What are your strengths and weaknesses?

Strengths: owning features end to end, integrations and APIs, and learning fast. Weakness (pick one that's true): for example, I used to spend too long perfecting something, so now I agree a "good enough" with the team and ship in small steps.

Debounce (JavaScript)

function debounce(fn, delay) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), delay);
  };
}

Fetch data in React with cleanup (TypeScript)

function Users() {
  const [users, setUsers] = useState<User[]>([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState<string | null>(null);

  useEffect(() => {
    const ctrl = new AbortController();
    fetch("/api/users", { signal: ctrl.signal })
      .then(r => { if (!r.ok) throw new Error("Request failed"); return r.json(); })
      .then(setUsers)
      .catch(e => { if (e.name !== "AbortError") setError(e.message); })
      .finally(() => setLoading(false));
    return () => ctrl.abort();
  }, []);

  if (loading) return <p>Loading...</p>;
  if (error) return <p>{error}</p>;
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}

Laravel: route, validation and eager loading

// routes/api.php
Route::post('/orders', [OrderController::class, 'store'])
     ->middleware('auth:sanctum');

// OrderController
public function store(Request $request)
{
    $data = $request->validate([
        'customer_id' => 'required|exists:customers,id',
        'items'       => 'required|array|min:1',
        'items.*.sku' => 'required|string',
        'items.*.qty' => 'required|integer|min:1',
    ]);
    $order = Order::create(['customer_id' => $data['customer_id']]);
    $order->items()->createMany($data['items']);
    return response()->json($order->load('items'), 201);
}

SQL practice

-- Top 5 customers by total spend
SELECT c.id, c.name, SUM(o.total) AS spend
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY spend DESC
LIMIT 5;

-- Duplicate emails
SELECT email, COUNT(*) AS n
FROM users
GROUP BY email
HAVING COUNT(*) > 1;

-- Customers with no orders
SELECT c.*
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- Second highest salary
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
