Story 2: reconciling sales to the cent with Shopify

S: Our dashboard's sales didn't exactly match Shopify's own sales report for the same dates.

Asked1. A customer is frustrated because an integration failed. How do you handle them while you investigate?
  1. Acknowledge and own it: "I understand. You've set time aside and it isn't working. I'm on it now and I'll stay on it until we know the cause."
  2. Get the facts quickly: which channel, which account or marketplace, what they clicked, the exact error message or a screenshot, and when it happened.
  3. Narrate, don't go silent: "I'm checking our logs for your account… the token was saved… now I'm testing the API call directly." No dead air.
  4. Try the quick fixes live: wrong account logged in, missing permission, a pop-up blocker, the wrong marketplace, a draft app missing version=beta. Many failures are fixed on the call.
  5. If it needs engineering, set expectations: "This needs our engineering team. I'll send them the request ID, timestamps and error now, and update you by 4 PM even if it isn't fixed yet." Give a time, not "soon".
  6. Offer a parallel path: connect the other channels now so the call still produces progress, or schedule a 15-minute follow-up.
  7. Close the loop: send a written summary (cause, fix, what they need to do, next step), then confirm with them once data appears.
  8. Prevent it next time: add it to the onboarding runbook, and tell Product if a pre-check would have caught it.
The customer mostly needs to feel someone competent owns the problem. So I acknowledge the impact, tell them exactly what I'm checking as I check it, give a concrete time for the next update, and follow through. Technically, I go from logs, to the stored connection, to a direct API call in Postman, so within minutes I know whether it's access, our sync, or the provider.
Asked2. Once the integration is done, how do you validate the data is synced and accurate?
  1. Agree the definitions first: which report the brand trusts (Seller Central Business Report, Shopify Analytics, the Ads console), their timezone, and whether sales include tax, shipping, cancellations and returns.
  2. Completeness, with counts: orders per day, source versus platform, for 3–7 sample days, including a busy day.
  3. Accuracy, with totals: sum of sales, units, ad spend, clicks per day. Then per marketplace and per SKU for the top items.
  4. Record-level spot checks: take 5–10 orders and compare them field by field (ID, date, status, items, amounts, currency).
  5. Duplicates and gaps: SQL with GROUP BY … HAVING COUNT(*) > 1 for duplicates, and LEFT JOIN … IS NULL for missing records. Also check for missing dates.
  6. Freshness: last successful sync time; is today's data arriving?
  7. Edge cases: refunds and returns, cancellations, Amazon Pending orders (no price yet), multi-currency, FBA vs merchant-fulfilled, the ad attribution window.
  8. Document known differences: e.g. "Ads sales use a 7-day attribution window, so recent days keep rising". Sign off with the client.
  9. Keep checking after go-live: automated reconciliation and alerts when a store's daily numbers deviate or a sync fails.
I validate in three layers: counts, totals, then individual records, always against the report the brand already trusts and in their timezone. Real example: our dashboard didn't match Shopify. Day-by-day SQL showed the difference was refund timing, not missing data. After we synced refunds by their own date, Groceryeshop matched to the cent: $11,939.37 and 298 orders for the month.
Asked3. The customer authorized the integration but no data shows. Troubleshoot it step by step.
  1. Scope it: which channel and data type (orders, ads, inventory)? Which date range do they expect? When did they authorize? Some data takes time: Amazon reports can take minutes to hours, and a first backfill takes longer.
  2. Check the connection record: is a refresh token saved? Is the seller ID, marketplace, region or ad profile correct? Status active?
  3. Check the sync jobs: did the initial import run? Is it queued, running, or failed? When was the last successful run?
  4. Read the logs for that account: 401, 403, 429, 400, or successful calls returning empty results?
  5. Reproduce in Postman with the same credentials. Get an access token, then call a simple endpoint: SP-API /sellers/v1/marketplaceParticipations, Ads API /v2/profiles, Shopify shop, GA4 runReport for the last 7 days.
  6. If the API returns data but the platform doesn't show it: the problem is ours. Check raw or staging tables, the mapping and transform, filters (marketplace, status, timezone or date boundaries), the dedup keys, and UI filters or caching.
  7. If the API returns nothing: wrong marketplace or region (India uses the EU endpoint), wrong ad profile, a vendor account authorized on the seller flow, wrong GA4 property (they gave the G- measurement ID), or simply no activity in that range.
  8. If the API returns an error: 401 = token or secret problem; 403 = missing role or scope, the user lacks permission, or the wrong region; 429 = throttling, so back off.
  9. Fix, re-sync the affected window, and verify with fresh data (counts and totals against the source).
  10. Tell the customer, then write it up: root cause in the runbook, and suggest a check at connection time so it can't happen silently again.
I split the problem in two: is the data coming from the provider, or are we losing it after that? A direct API call in Postman with the customer's token answers that in minutes. If the API returns data, I trace it through our pipeline: raw tables, mapping, filters, timezone. If it doesn't, I check the account side: role or scope, marketplace and region, ad profile, the user's permissions. In my platform, every connection has a Test button that runs exactly this check and explains the result in plain words.

Asked5. How do you handle data mapping and data synchronization?

Mapping

  • A mapping sheet per channel: source field → platform field, data type, transform, example value, required or optional.
  • Transforms: timezones (store UTC, report in the brand's timezone), currency, status mapping (Amazon Shipped/Unshipped/Canceled; Shopify financial_status + fulfillment_status → one platform status), and units versus amounts.
  • Keys: a natural unique key per record (e.g. store_id + order_id), so re-syncing updates rows instead of duplicating them.
  • Identity across channels: SKU ↔ ASIN ↔ Shopify variant ↔ Flipkart listing. This is often the hardest part, so get a master SKU sheet from the brand.

Synchronization

  • Initial backfill through bulk paths (Amazon Reports API, Shopify bulk operations), then incremental syncs by "updated since" (LastUpdatedAfter, updated_at), plus webhooks or notifications for speed.
  • A re-sync window for late changes (ad conversions about 14 days, GA4 a few days, refunds and returns).
  • Idempotent upserts, checkpointing (cursor or NextToken), retries with backoff for 429/5xx, and a job log per run.
  • Reconciliation job: polling as a safety net for missed webhooks, plus daily count and total checks.
In Commerce Optimizer, I backfill Shopify history with one bulk export, then fetch orders changed since the last sync on a schedule. Refunds and edits change an order's updated_at, so they're picked up too. Writes are batched upserts on a unique key, so syncs never duplicate. Ads data re-syncs the last 14 days because conversions arrive late.

AskedHow would you connect a Shopify merchant to a SaaS platform using OAuth?

See the full answer, with code, under Shopify and FastAPI. The short version:

  1. The merchant clicks Install / Connect and enters their shop.myshopify.com.
  2. Redirect to /admin/oauth/authorize with client_id, minimal scope (e.g. read_orders,read_products,read_inventory), redirect_uri, and a random state.
  3. The merchant approves the scopes. Shopify redirects back with code, shop, state and hmac.
  4. Verify the HMAC with the app secret, check that state matches and that shop is a valid *.myshopify.com domain.
  5. POST https://{shop}/admin/oauth/access_token with client_id, client_secret and code to get an offline access token plus the granted scopes. Store it encrypted.
  6. Register webhooks (orders/create, orders/updated, app/uninstalled), start the backfill, and show "connected".
  7. Re-authorization: when scopes change, compare the granted scopes with the required ones and send the merchant through the authorize URL again. On 401 or app/uninstalled, mark the connection disconnected and ask the merchant to reconnect.

Amazon SP-API deep dive

The focus of Shaun's questions. Know the vocabulary and the order of steps.

Key concepts

Seller vs vendor

  • Seller (3P): sells directly to customers through Seller Central; owns price and stock; FBA or merchant-fulfilled. Data: Orders, FBA Inventory, Listings, Catalog, Finances, Reports, Notifications.
  • Vendor (1P): sells wholesale to Amazon through Vendor Central; Amazon is the retailer. Data: purchase orders, shipments, invoices, direct fulfilment, and vendor retail analytics reports (sales, traffic, inventory).
  • Separate consent URLs (vendorcentral.amazon.in/apps/authorize/consent), different APIs, different reports. Always ask which one on the kickoff call.

Developer profile and roles

  • Private developer: builds for their own business. Public developer: builds for other sellers (a SaaS like Amplicomm).
  • Roles = data access you request, e.g. Product Listing, Pricing, Inventory and Order Tracking, Amazon Fulfillment, Finance and Accounting, Brand Analytics, Selling Partner Insights.
  • Restricted roles (buyer PII: addresses, tax) need extra review and a Restricted Data Token (RDT) per call.
  • Approval can take days, and Amazon may come back with questions. Start it early, and set the client's expectations.

LWA (Login with Amazon)

  • The app has an LWA client ID and client secret. The secret must be rotated periodically; an expired secret causes invalid_client.
  • Seller consent gives an spapi_oauth_code (valid about 5 minutes), which is exchanged for a refresh token (long-lived) and an access token (1 hour).
  • Refresh: grant_type=refresh_token at https://api.amazon.com/auth/o2/token.
  • Grantless operations (e.g. creating Notifications destinations) use grant_type=client_credentials with a scope like sellingpartnerapi::notifications.

Regions and marketplaces

  • NA: sellingpartnerapi-na.amazon.com: US ATVPDKIKX0DER, CA A2EUQ1WTGCTBG2, MX, BR
  • EU: sellingpartnerapi-eu.amazon.com: IN A21TJRUUN4KGV, UK A1F83G8C2ARO7P, DE A1PA6795UKMFR9, AE A2VIGQ35RCS4UG, and others
  • FE: sellingpartnerapi-fe.amazon.com: JP A1VC38T7YXB528, AU, SG
  • Sandbox: sandbox.sellingpartnerapi-… (static mock responses)

Shopify

App types

  • Custom app created in the store admin: Settings → Apps and sales channels → Develop apps → create → set Admin API scopes → install → reveal the Admin API token once (shpat_…). Quick for one store; the token is shown only once.
  • Public app (Partner Dashboard): many merchants install through OAuth. Can be listed on the App Store. Must handle the mandatory privacy webhooks.
  • Custom distribution app: built in the Partner/Dev Dashboard for one merchant or organisation, installed through an install link and OAuth.

  • Collaborator account: a partner requests access to the store from the Partner Dashboard (the store may require a collaborator request code from Settings → Users). The owner approves and picks the permissions.
  • Staff account: the owner invites a user with specific permissions.
  • For onboarding calls: you'll often need the owner, or a staff member with "Develop apps" and "Manage apps" permissions.

OAuth flow (public or custom-distribution app)

  1. Install request → validate the shop parameter (^[a-zA-Z0-9][a-zA-Z0-9\-]*\.myshopify\.com$).
  2. Redirect: https://{shop}/admin/oauth/authorize?client_id=…&scope=read_orders,read_products&redirect_uri=…&state=<nonce>. Add &grant_options[]=per-user for an online (per-user, expiring) token. The default is an offline token for background syncs.
  3. Callback: verify hmac (HMAC-SHA256 of the sorted query string without hmac, using the app secret), check state and shop.
  4. POST https://{shop}/admin/oauth/access_token with {client_id, client_secret, code} → {access_token, scope}. Check that the granted scopes cover what you need.
  5. Store the token encrypted. Use the header X-Shopify-Access-Token. Register webhooks and start the backfill.
  6. Embedded apps can use Shopify-managed installation and token exchange (session token → access token) instead of the redirect dance. Same idea.

Scopes worth knowing

read_orders (last 60 days only), read_all_orders (older history, needs approval for public apps), read_products, read_inventory, read_customers (protected customer data rules apply), read_fulfillments, read_returns, read_analytics, read_reports, read_discounts. Principle: request the minimum you need.

Webhooks

  • Topics: orders/create, orders/updated, orders/cancelled, refunds/create, products/update, inventory_levels/update, app/uninstalled.
  • Verify X-Shopify-Hmac-Sha256: base64 HMAC-SHA256 of the raw body with the app secret. Compare in constant time.
  • Reply 200 quickly (within about 5 seconds), then process in the background. Shopify retries failed deliveries a limited number of times, and repeated failures can remove the subscription. Webhooks can arrive twice or out of order: dedupe with X-Shopify-Webhook-Id and use updated_at to decide which version is latest.
  • Never rely on webhooks alone: run a reconciliation poll (updated_at_min) for missed events.
  • Public apps must handle the privacy webhooks: customers/data_request, customers/redact, shop/redact.

Limits, versions and bulk

  • REST: leaky bucket per app per store (e.g. 40 requests, refilling at 2 per second on standard plans); 429 with Retry-After. REST is now legacy, and new public apps are expected to use GraphQL.
  • GraphQL: cost-based limits; read extensions.cost.throttleStatus. Cursor pagination with pageInfo { hasNextPage endCursor }.
  • Bulk operations (bulkOperationRunQuery) export large datasets as JSONL. You used this for history imports.
  • API versions are quarterly (2026-07 etc.), each supported for about a year. Pin a version and upgrade on schedule.

TechHTTP methods and idempotency

GET reads (safe, idempotent) · POST creates or triggers (not idempotent) · PUT replaces (idempotent) · PATCH partial update · DELETE removes (idempotent). Idempotent means repeating the same call has the same effect. That matters for retries, so use idempotency keys on POSTs that create things.

TechWhat's in an HTTP request and response?

Request: method, URL (path and query parameters), headers (Authorization, Content-Type: application/json, Accept) and body. Response: status code, headers (Content-Type, rate-limit headers, Retry-After, Link for pagination) and body (JSON). When debugging, always capture the request ID header to give the provider.

TechPagination types
  • Offset/limit (page=3&limit=50): simple, but records shift if the data changes during the read.
  • Cursor (Shopify endCursor, Amazon NextToken, REST Link header): stable. Loop until there's no next cursor.
  • Time-window (updated_since): for incremental syncs; overlap windows slightly.

A classic "missing data" bug is reading only the first page.

TechRate limits: how do you handle them?

Read the provider's model (token bucket, leaky bucket, cost points). Throttle per account. On 429: exponential backoff with jitter (1s, 2s, 4s… capped) and respect Retry-After. Use bulk or report APIs for large pulls, cache what doesn't change, and spread scheduled syncs out so they don't all fire at once.

TechWebhooks vs polling

Webhooks push changes the moment they happen, so they're efficient, but they can be missed, duplicated or arrive out of order. Polling is reliable but slower and uses quota. Best practice is both: webhooks for speed, a periodic reconciliation poll for correctness, and idempotent processing (dedupe by event ID, last-write-wins by updated_at). Secure webhooks with HMAC signatures over the raw body, HTTPS only, and a fast 200 reply.

TechJSON basics they may probe

Objects {}, arrays [], strings, numbers, booleans, null. Watch out for: money as strings in some APIs ("Amount": "499.00"), nested objects (OrderTotal.Amount, OrderTotal.CurrencyCode), a missing key vs null, ISO 8601 dates (2026-11-05T13:00:00Z), and large IDs that lose precision as JavaScript numbers (keep them as strings).

import httpx

LWA_URL = "https://api.amazon.com/auth/o2/token"
SPAPI_EU = "https://sellingpartnerapi-eu.amazon.com"   # India is in the EU region
INDIA = "A21TJRUUN4KGV"

async def get_access_token(client: httpx.AsyncClient, refresh_token: str) -> str:
    r = await client.post(LWA_URL, data={
        "grant_type": "refresh_token", "refresh_token": refresh_token,
        "client_id": LWA_CLIENT_ID, "client_secret": LWA_CLIENT_SECRET})
    if r.status_code == 400 and r.json().get("error") == "invalid_grant":
        raise NeedsReauthorization()                  # tell the brand to reconnect
    r.raise_for_status()
    return r.json()["access_token"]                   # valid for 3600 seconds

async def fetch_orders(refresh_token: str, last_updated_after: str) -> list[dict]:
    orders: list[dict] = []
    async with httpx.AsyncClient(timeout=30) as client:
        token = await get_access_token(client, refresh_token)
        params = {"MarketplaceIds": INDIA, "LastUpdatedAfter": last_updated_after}
        attempt = 0
        while True:
            r = await client.get(f"{SPAPI_EU}/orders/v0/orders", params=params,
                                 headers={"x-amz-access-token": token})
            if r.status_code == 429:                  # throttled
                attempt += 1
                await asyncio.sleep(min(60, 2 ** attempt) + random.random())
                continue
            if r.status_code == 401:                  # token expired mid-run
                token = await get_access_token(client, refresh_token)
                continue
            r.raise_for_status()
            attempt = 0
            payload = r.json()["payload"]
            orders.extend(payload.get("Orders", []))
            next_token = payload.get("NextToken")
            if not next_token:
                return orders
            params = {"MarketplaceIds": INDIA, "NextToken": next_token}

FastAPI questions

TechWhy FastAPI over Flask or Django?

It's async-first (good for I/O-heavy integration calls), validates requests and responses from type hints with Pydantic, generates OpenAPI docs automatically, and performs well. Flask is simpler and synchronous by default. Django is a full framework with an ORM and admin, which is heavier for a pure API.

TechWhat happens when a request body fails validation?

FastAPI returns 422 Unprocessable Entity with a JSON list of which field failed and why. You can customise it with an exception handler for RequestValidationError.

TechHow do you protect an endpoint?

A dependency, e.g. OAuth2PasswordBearer or a custom header check, that verifies the token or API key and returns the current user; add Depends(get_current_user) to the route or router. For webhooks: HMAC verification on the raw body. Plus HTTPS, CORS rules and rate limiting.

TechHow would you run long syncs?

Not in the request. The endpoint enqueues a job (Celery, RQ or Arq with Redis, or a DB jobs table claimed with SELECT … FOR UPDATE SKIP LOCKED, which is what you built) and returns 202 with a job ID. Workers run the job with retries and checkpoints, and the UI polls the status.

TechPython basics they may slip in
  • List vs tuple vs dict vs set; list and dict comprehensions.
  • requests (sync) vs httpx (sync and async); json.loads / json.dumps.
  • try / except / finally; raising custom exceptions.
  • Virtual environments (python -m venv), pip install -r requirements.txt.
  • datetime with timezones (zoneinfo.ZoneInfo("Asia/Kolkata")); Decimal for money, never float.

Database questions

DBINNER vs LEFT JOIN?

INNER returns only matching rows on both sides. LEFT returns every row from the left table, with NULLs where the right side has no match. That's why LEFT JOIN … WHERE right.id IS NULL finds missing records.

DBWHERE vs HAVING?

WHERE filters rows before grouping; HAVING filters groups after aggregation (HAVING COUNT(*) > 1).

DBPrimary key vs unique key vs foreign key?

Primary key: unique, not null, one per table, identifies the row. Unique key: no duplicates (one NULL may be allowed, depending on the DB), and several are allowed. Foreign key: references another table's key to keep the data consistent (e.g. orders.store_id → stores.id, cascading deletes). For integrations, a unique key on (store_id, source_order_id) is what makes upserts idempotent.

DBWhat is an index? When does it hurt?

A sorted structure (B-tree) that makes lookups, joins and range scans fast. Composite indexes follow the leftmost-prefix rule: (store_id, date) helps WHERE store_id = ? AND date BETWEEN … but not WHERE date = ? alone. Costs: slower writes and extra storage. Check queries with EXPLAIN.

DBWhat are transactions and ACID?

Atomicity (all or nothing), Consistency (constraints hold), Isolation (concurrent transactions don't interfere), Durability (committed means saved). Example: replace a day's ad rows in one transaction, deleting the old rows and inserting the new ones, so dashboards never see half the data.

DBWhy DECIMAL for money and UTC for time?

FLOAT has rounding errors (0.1 + 0.2 ≠ 0.3), so money uses DECIMAL(14,2). Store times in UTC, convert to the brand's timezone for reporting, and keep each store's timezone. Day boundaries are the number-one cause of "your numbers don't match".

DBDELETE vs TRUNCATE vs DROP; UNION vs UNION ALL?

DELETE removes rows (can have a WHERE; logged; can be rolled back). TRUNCATE empties the whole table quickly and resets auto-increment. DROP removes the table itself. UNION removes duplicates; UNION ALL keeps them and is faster.

DBNormalization vs denormalization for analytics?

Normalize transactional data (orders, items, refunds) to avoid duplication and anomalies. For dashboards, build daily aggregate tables (store × date × channel) so queries are fast. That's what you did: daily totals rebuilt from the stored orders.

DBOLTP vs OLAP; SQL vs NoSQL?

OLTP: many small reads and writes (the app's database). OLAP: big aggregations (warehouses like BigQuery, Redshift, ClickHouse). SQL: structured, relational, joins and constraints. NoSQL: flexible documents or key-value, good for raw API payloads and logs. Many integration platforms keep the raw JSON alongside the mapped tables so they can reprocess it.

DBA query on orders became slow. What do you do?

EXPLAIN it: look for a full table scan, a missing index, functions applied to indexed columns (DATE(col) blocks index use, so use a range instead), SELECT *, or N+1 queries from the app. Add or adjust a composite index, paginate, or pre-aggregate.

Troubleshooting playbooks

The universal method: scope → connection → jobs → logs → reproduce in Postman → split "provider vs us" → fix → re-sync → verify → close the loop.

Playbook401 Unauthorized
  1. Is the access token expired? Refresh it and retry.
  2. If the refresh fails with invalid_grant: the token was revoked or the authorization expired, so the brand must reconnect.
  3. Is the header right? (x-amz-access-token vs Authorization: Bearer vs X-Shopify-Access-Token.)
  4. invalid_client: the client secret was rotated or expired. Update it in the vault.
Playbook403 Forbidden
  1. Does the token's scope or role cover this endpoint? (Missing SP-API role, missing Shopify scope.)
  2. Region and endpoint: an India seller on the NA endpoint gives a 403.
  3. Ads: is the profile ID header correct and from the same region?
  4. Google Ads: login-customer-id missing, or the account isn't linked to the MCC.
  5. GA4: the service account or user isn't on the property.
  6. The user who authorized lost their permission in the account.
Playbook429 / slow sync
  1. Check the rate-limit headers; identify the operation.
  2. Backoff with jitter; reduce concurrency per account.
  3. Move bulk pulls to the Reports API or bulk operations.
  4. Stagger scheduled syncs across accounts.
PlaybookPartial data (some days or orders missing)
  1. Pagination: did we follow every NextToken or cursor?
  2. Date boundaries: UTC vs local; inclusive or exclusive end dates.
  3. Status filters: Pending or Cancelled excluded on purpose?
  4. Scope limits: Shopify's 60 days without read_all_orders; Ads report retention.
  5. Failed job runs in that window: re-run the window.
PlaybookDuplicates
  1. Find them with GROUP BY / HAVING.
  2. Cause: no unique key, a webhook plus a poll both inserting, a retry after a timeout that actually succeeded.
  3. Fix: a unique key plus upsert; dedupe events by ID; clean up with ROW_NUMBER.
PlaybookTotals don't match the channel's report
  1. Same date range and timezone?
  2. Same definition: tax and shipping included? Refunds by order date or refund date? Cancellations?
  3. Attribution windows (ads: 7 or 14 days) and late data (re-sync recent days).
  4. Currency (multi-marketplace).
  5. Narrow it to the day, then to the order, and compare field by field.
PlaybookOAuth consent fails during the call
  1. redirect_uri mismatch: it must match exactly (https, trailing slash).
  2. Wrong account logged in: ask them to log out of other Amazon or Google accounts, or use an incognito window.
  3. The user lacks admin or app-management rights.
  4. Draft SP-API app without version=beta.
  5. Pop-up or cookie blockers; an expired state or code (they took longer than the code's lifetime, about 5 minutes for Amazon), so restart the flow.

Rapid-fire Q&A

One-line answers. Click to reveal.

What is LWA?
Login with Amazon: Amazon's OAuth 2.0 service, which issues the tokens for both SP-API and the Ads API.
How long does an SP-API access token last?
1 hour (3600 seconds). Refresh it with the refresh token.
Which SP-API endpoint is used for India?
EU: sellingpartnerapi-eu.amazon.com, marketplace A21TJRUUN4KGV.
Do SP-API calls still need AWS SigV4 signing?
No. Since late 2023 the LWA access token in x-amz-access-token is enough.
What's an RDT?
A Restricted Data Token, from the Tokens API, needed to read PII such as buyer names and addresses. It requires restricted roles.
How do you get bulk order history from Amazon?
The Reports API (create report → poll → get document → download), not paging through getOrders.
How does Amazon push events?
The Notifications API, delivering to SQS or EventBridge. Not plain HTTP webhooks.
What does the Amazon-Advertising-API-Scope header hold?
The advertising profile ID (one per marketplace and account).
What's the first Ads API call after authorization?
GET /v2/profiles, to find the profile IDs.
What is ACoS vs TACoS?
ACoS = ad spend ÷ ad-attributed sales. TACoS = ad spend ÷ total sales (needs SP-API sales too).
Seller vs vendor in one line?
A seller (3P) sells to customers on Seller Central; a vendor (1P) sells wholesale to Amazon on Vendor Central.
Shopify offline vs online token?
Offline: for the app's background work, long-lived. Online: tied to one user's session, expires.
How do you verify a Shopify webhook?
Base64 HMAC-SHA256 of the raw body with the app secret, compared in constant time with X-Shopify-Hmac-Sha256.
Which scope gives Shopify orders older than 60 days?
read_all_orders.
What is the state parameter for?
CSRF protection: a random value sent in the authorize URL and checked on the callback.
What does GA4 need: the measurement ID or the property ID?
The numeric property ID for the Data API. G-XXXX is the measurement ID used for tagging.
Google Ads login-customer-id?
The manager (MCC) account ID, without dashes, when you access a client account through the manager.
Google refresh tokens expire after 7 days. Why?
The OAuth consent screen is in "Testing". Publish the app (move it to production).
401 vs 403?
401: who are you? (bad or expired credentials). 403: I know who you are, and you're not allowed (scope, role, permission).
What's idempotency?
Doing the same operation twice gives the same result. You get it with unique keys and upserts, or idempotency keys.
Exponential backoff?
Retry after 1s, 2s, 4s, 8s… plus random jitter, up to a cap. Respect Retry-After.
PUT vs PATCH?
PUT replaces the whole resource; PATCH updates part of it.
What does a 422 mean in FastAPI?
The request failed Pydantic validation.
Where are FastAPI's docs?
/docs (Swagger UI) and /redoc.
Why store a refresh token encrypted?
It grants long-term access to the brand's data. Treat it like a password: encrypted at rest (e.g. AES-256-GCM), never sent to the browser, access logged.
What's UAT?
User Acceptance Testing: the client or business confirms the integration and data meet their needs before go-live.
What's a sandbox?
A test environment with mock or test data (the SP-API sandbox, Shopify development stores, Google Ads test accounts).
What's the difference between OMS, WMS and ERP?
OMS manages orders across channels; WMS manages warehouse stock and picking; ERP runs finance, procurement and inventory across the business. You built middleware between Shopify and the ERP.
